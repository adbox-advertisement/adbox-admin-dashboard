# Application architecture

AdBox uses feature-first modules with a shared application shell. Only implemented modules have source directories. Planned modules remain in `src/config/pending-pages.ts` until they have their own behavior.

## Ownership and dependencies

```text
main.tsx
└── app/                         App + providers + QueryClient
    └── routes/                  Guards, public paths, router composition
        ├── layouts/             Shared authenticated shell
        └── features/
            ├── auth/            API, mutation hooks, login page
            ├── dashboard/       Widgets, charts, display datasets
            ├── admins/          Admin accounts, roles and permission assignments
            ├── users/           Platform users (sign-ups), profiles, suspension, institution verification
            ├── content/         User-uploaded videos, pictures, text posts, ads and surveys; moderation
            ├── recruitment/     Applicant queue, full submissions, reviews and response drafts
            ├── settings/        Workspace preferences, beginning with Appearance
            ├── support/         Help desk on sample data (no support API yet)
            ├── rewards/         Partners and gold-bar redemptions on sample data (no rewards API yet)
            ├── videos/          Upload, folders, Posts
            └── rdi/             Website CMS, local drafts, website screens and previews

components/{ui,layout,feedback}/  Shared controls, navigation, page feedback
config/                          Navigation, pending pages, environment
api/                             Axios transport and session refresh
lib/                             Session storage and shared helpers
assets/{brand,dashboard,posts,schools}/
styles/                          Shared typography, colors, shadows
```

Each feature exposes its supported public API through `index.ts`. These entry points export route definitions without eagerly importing page components. Inside a feature, use relative imports. Outside it, use `@/features/<name>`; avoid reaching into private files. Shared controls and helpers must not import domain features or the application shell.

Small features use `api.ts`, `hooks.ts`, and `types.ts`. Split these into directories when responsibilities grow. Do not add empty service, hook, or store files just to match a template.

`npm run check:architecture` checks static imports, re-exports, and literal dynamic imports against these boundaries, prevents UI from directly importing API services, and detects runtime import cycles. Type-only imports do not create runtime cycles. TypeScript checks unresolved source imports during the build.

## Routing and navigation

`src/routes/paths.ts` defines stable URLs. Feature `routes.ts` files own their pages and lazy imports. `src/routes/router.ts` composes public, protected, pending, and not-found routes.

Protected routes share `DashboardLayout` and recheck the local session on navigation. Route metadata supplies the title and optional workspace layout. RDI provides lazy CMS pages at `/rdi`, a nested website layout at `/rdi/website`, and separately guarded standalone previews at `/rdi/preview/:pageId`. The previews render without `DashboardLayout` and also power the editor iframe. Video Management provides a nested Upload/Posts layout. The sidebar persists across page changes and uses `src/config/navigation.ts` for labels and groups.

Waiting work is shown on the sidebar (`src/features/activity`, backend `docs/super-admin-api.md` "Live activity"). `DashboardLayout` calls `useLiveActivity()` once: it fetches `GET /activity/counts` and opens a Socket.IO connection to super-admin's `/admin` namespace (path `/api/v1/socket.io`, through the Vite `/api` proxy with `ws: true`). Each `activity:count` updates the counts, refreshes that queue's feature queries, and, when work was added, shows a toast and plays a chime generated with Web Audio (one per burst across tabs; turned off in **Settings → Notifications**, stored as `adbox-activity-sound`). A refused or ended socket session is renewed through the REST client and reconnected; while the socket is down the counts are polled every minute. The layout turns counts into route badges (`activityBadges`) and provides them through `NavBadgesContext` (`src/components/layout/nav-badges.ts`), so the shared sidebar and mobile menu buttons never import the feature. A section's badge is the sum of its entries; a queue the admin cannot open is absent, so it has no badge.

Initial navigation has a loading screen. Page changes have an accessible loading indicator. Route errors have a recovery screen; unknown URLs return a not-found screen. Backend authorization is required independently of browser route guards.

`AppProviders` mounts the shared `WorkspaceTheme` above the router. One
`next-themes` provider controls the root `.dark` class, color scheme, and Sonner
notifications across authentication, dashboard features, RDI/CMS, standalone
previews, loading/error screens, and Radix portals. The single `ThemeToggle` is
mounted only in **Settings → Appearance** at `/settings`; headers, candidate
profiles, sign-in, and RDI previews inherit the selected theme. The preference is
stored as `adbox-theme` and synchronizes across browser tabs and preview iframes;
an existing `adbox-recruitment-theme` preference is migrated on first use. The
default is light. Theme changes do not modify CMS documents or other feature data.
Shared semantic tokens and explicit dark variants cover surfaces, charts, forms,
tables, borders, and labels; brand artwork and media retain their original colors.
`compactHeader: true` route metadata selects the compact header layout (no route
uses it since Recruitment moved to the standard header) and has no effect on theme
scope.

## Server and client state

```text
API response → feature API service → TanStack Query hook → page / component
User input → component state or feature UI store
```

`src/api/client.ts` owns the configured Axios instance, timeout, authorization header, and single-flight token refresh. `src/lib/auth-session.ts` validates session records and retains the existing session-storage key. Authentication actions do not trigger token refresh; the protected `GET /auth/me` profile request does. Logout clears the session and Query cache, including when the server logout request fails.

The authenticated dashboard header displays the current email and assigned roles from `GET /auth/me`. Auth validates this response, including effective permissions used by feature controls, and keeps it in TanStack Query, separately from session tokens. A successful sign-in removes previous queries so account and RBAC data cannot carry over between accounts. `DashboardLayout` supplies the auth-owned profile component through the shared header's account slot, with loading and retry states; RDI workspace routes do not mount it or request profile data.

Manage Admins (`src/features/admins/`) has routes for Admins (`/manage-admins/admins`, `/:adminId`), Roles (`/manage-admins/roles`, `/:roleId`) and Permissions (`/manage-admins/permissions`); `/manage-admins` redirects to Admins and the sidebar lists the three. It uses `GET/POST/PATCH /admins`, `PUT /admins/:id/roles|permissions`, `GET/POST/PATCH/DELETE /roles`, `PUT /roles/:id/permissions` and `GET /permissions`. `admins/api.ts` validates raw responses and maps nested assignments; `admins/hooks.ts` owns the queries and mutations (every write invalidates accounts, roles, the catalogue and the current admin's permissions, even after an ambiguous failure) and `useViewer()` (id, Super Admin or not, permission check). `lib/catalog.ts` names permissions in words, groups them into areas, marks sensitive ones, turns role keys into titles and back, and works out an admin's effective access with its sources. `lib/access.ts` mirrors the API rule that every access change is the Super Admin's (backend `admins/admin-access.policy.ts` and `@RequireRoles(SUPER_ADMIN_ROLE)`), so screens offer only what the API will accept and explain the rest. No account or RBAC data is stored in Zustand.

Role metadata and permission assignments have separate save actions because the backend provides separate writes. Creating a role opens its permission editor when the account can assign and read permissions; cancelling that editor leaves the saved role with no permissions. Names follow the backend's uppercase identifier format, descriptions are optional, and an empty `permissionIds` array clears the complete assignment set. System roles are read-only in this UI and the wildcard permission is never offered for assignment through role editing. Controls use effective permissions from `GET /auth/me`; the backend independently enforces authorization.

The **Admin** tab uses `GET /admins`, `GET /admins/:id`, `POST /admins`, `PATCH /admins/:id`, `PUT /admins/:id/roles`, and `PUT /admins/:id/permissions`. It displays all assigned roles and active status, and filters by live role IDs. Account details are fetched on opening an action before initializing editable fields or a replacement assignment set. Create accepts optional names, email, a 5–128 character password and optional initial role IDs in one request. Passwords stay in the create form/request, are stripped from parsed responses, and the create mutation is reset after success with immediate cache garbage collection when unobserved.

**Manage Users** (`/manage-users`, `src/features/users/`) is one layout route (`ManageUsersLayout`: permission gate, first-allowed-section and legacy `?user=<id>` redirects) with lazy children: Overview (index), `people`, `people/:userId`, `institutions`, `institutions/:institutionId`, `companies`, `companies/:companyId`, `verification`, `business-requests[/:requestId]`, `page-requests[/:requestId]` and `honours`. Each child route's handle titles the page header ("People", "Business request"…). Only the sidebar moves between sections: its Manage Users sub-items are grouped **Directory** (People, Institutions, Companies) and **To review** (Verification, Business requests, Page requests, Honours) through the optional `group` on a navigation child; a child owns its nested paths. Overview opens on **Waiting for review** (one tile per queue the admin may open) before the figures. List pages share one anatomy from `components/ListParts.tsx`: `PageIntro` (one line on what the page holds), then a card whose `ListToolbar` holds `StatusFilter` (counts shown when non-zero) and `SearchField` over the table. Queue rows open a review page (`Review`/`View`); verification is decided in its row. Endpoints: `GET /platform-users` (server-side `search`, `role`, `affiliation`, `status`, `verificationTier`, `badge`, `institutionId`, `campusId`, `page`, `limit`; items carry follower/following/company counts), `GET /platform-users/stats[?institutionId]` (role, status, affiliation, verification and badge totals, members per institution and, when scoped, per campus), `GET /platform-users/:id`, `/relationships` and `/connections?direction=followers|following|blocking|blockedBy`, `PATCH /platform-users/:id` and `/badges`, `POST /platform-users/:id/suspend|reactivate`, `GET /companies` and `/companies/:id` (with publishers), `POST /companies/:id/approve|reject`, `GET /honour-review[/:userId]`, `POST /honour-review/:userId/grant|decline`, `GET|POST /verification-requests…` and `GET /institutions`. People filters live in the URL (`lib/people-filters.ts`) so Overview figures link to filtered lists. Breakdowns use one hue per bar with labelled counts and shares, never colour-coded categories. Sections and actions follow `platform.users.*` (including `badges`), `verification.*`, `companies.*`, `honours.review` and `institutions.read`; the backend remains authoritative. Account status distinguishes an AdBox suspension from the owner's own deactivation, pending deletion or erasure; staff can only suspend and reactivate the first.

**User Content** (`/user-content`, `src/features/content/`) is a layout (`UserContentLayout`: permission gate, uploader scope banner) with sub-pages: Overview, Posts (`/posts`, one library for every format, plus `/posts/:postId`), Ads (one uploader's ads; details in a side sheet), Surveys, and Reports (`/reports`, the moderation queue, plus `/reports/:reportId` and `/reports/messages/:reportId`). Each child route's handle titles the page header. The sidebar lists Overview, **Content** (Posts, Surveys) and **To review** (Reports); there is no in-page section bar. Ads is not in the sidebar: everyone's ads are in Ads Management, so `/user-content/ads` without `?userId=` redirects there and the Overview's "Ads running now" links there. While an uploader is selected, the banner ("Showing content by …") carries that uploader's own Overview, Posts, Ads and Surveys links and "Show everyone". Each list page opens with a `PageIntro` line (`components/ContentBits.tsx`). It uses the super-admin `user-content` endpoints (in `adbox-backend/apps/super-admin/src/user-content/`): `GET summary|uploaders|posts|posts/:id|ads|surveys`, `POST posts/:id/remove|restore`, `POST surveys/:id/deactivate|reactivate`, `GET reports|reports/:id`, `POST reports/:id/resolve` (optionally removing the post or comment), and `GET chat-reports|chat-reports/:id`, `POST chat-reports/:id/resolve`. Reads need `user.content.read`; writes need `user.content.moderate`. `?userId=` scopes every section except Reports to one uploader, list filters live in the URL, and old `?tab=` links redirect to the matching section. Admin removal sets `deleteStatus = DELETED`, so restore never revives an author's own deletion. Ads are read-only here; decisions on ads (review, pausing, reports) are made in Ads Management. The feature uses its own `lib/cn.ts`, because the shared `cn` drops the theme's `text-h*`/`text-b*` sizes when they are combined with a text colour.

Profile editing changes names only; email is read-only. Role and direct-permission replacement have separate dialogs and support empty sets. Direct permissions are additive to role-derived access; clearing direct permissions keeps assigned roles. The direct-permission picker supports the backend's wildcard assignment, while the permission picker for role editing excludes it. The UI prevents changing the current admin's own roles/direct permissions or deactivating their account, matching backend restrictions. Deactivate/reactivate uses `PATCH` with `isActive`; there is no account-delete endpoint. Photo upload, telephone and notification controls were removed from the active form because the backend does not support them. Permission-definition creation/editing/deletion remains outside this integration.

Feature API services contain endpoints and transport mappings. Hooks own queries, mutations, invalidation, and loading state. RDI has no API services or Query hooks. Its Zustand store owns local authoring drafts, save state, and undo/redo history; this is browser content, not a duplicate of server state. The document is validated with Zod when read from storage, restored from a backup, or received by a preview. Storage errors remain visible and preserve the in-memory draft for export.

Video folders currently represent local authoring groups. The feature store persists folder metadata and selection; it does not store API responses. File objects, object URLs, and unfinished composer text stay in mounted upload components. Do not treat these as durable server content. A future upload API should use services and Query hooks, while keeping selection, dialogs, and filters in client state.

## Feature organization

- **Auth:** the API validates returned sessions and the current-admin profile; mutation hooks drive sign-in, and a Query hook supplies the header's email and roles.
- **Recruitment:** lazy `/recruitment` route with authenticated Axios services, Zod response/form schemas, and TanStack Query list/detail/stats/campaign queries. The queue uses server pagination/search/filtering, and queue/statistics poll every minute. The page leads with the pipeline (stage counts that filter the list) and a next-step column; per-campus accepted/in-progress counts come from `byInstitution[].byStatus` when the server sends it. Detail exposes all 14 applicant answers, on-demand private video, a stage tracker with one next-step action (plus reject/withdraw, each with a note), review notes/rating with actor-resolved history, and manual email drafts. Mutations invalidate recruitment data even on failure; permission gates come from the current admin profile. Detail/video data is discarded from its query/mutation cache when unobserved; filters and draft input remain local component state. No recruitment data is persisted in Zustand or browser storage. CSV comes from the audited backend export; unsupported text-search filtering is explained before download. See [RECRUITMENT.md](RECRUITMENT.md) for contracts, fields, retention behavior, and current limitations. Tracked applicant responses require the proposed backend extension in [RECRUITMENT_RESPONSES_BACKEND.md](RECRUITMENT_RESPONSES_BACKEND.md).
- **Admins:** `api.ts`, `hooks.ts`, and `validation.ts` own backend account/RBAC integration. Components render account and role tables, profile/status/assignment dialogs, loading/retry states and CSV exports. Both old mock stores and catalogs have been removed; only form input, filters, selections and dialog visibility remain in component state.
- **Support:** lazy `/support` route (it replaced the pending page). There is no support API: `api.ts` serves an in-memory sample desk (`data/sample-desk.ts`, timed relative to now, ~250 ms latency, `resetSampleDesk()`) behind the same functions a real service would have (`getTickets`, `getTicket`, `getSupportSummary`, `getSavedReplies`, `replyToTicket`, `updateTicket`), and `hooks.ts` wraps them in TanStack Query, so connecting a service means replacing `api.ts` only. `lib/desk.ts` holds the views, urgency order, reply-deadline states and labels. The page: sample banner, figures, views with counts, search/topic/order, list and conversation side by side from `lg` (list then conversation on phones), customer details in a rail from `2xl`, J/K/R/`/` shortcuts. A reply moves a ticket to waiting on the customer (or resolves it) and is never sent; internal notes change nothing else.
- **Rewards:** lazy `/rewards`, `/rewards/requests`, `/rewards/catalog`, `/rewards/partners` and `/rewards/partners/:partnerId` routes; the sidebar entry groups them (Overview · To review: Redemption requests · Manage: Rewards catalog, Partners). There is no rewards API: `api.ts` serves an in-memory sample (`data/sample-rewards.ts`: 4 partners, 12 offers, 12 people, 15 current requests and 46 older deliveries, timed relative to now; `sampleRewards.latency`/`deliveryMs`, `resetSampleRewards()`) behind the functions a real service would have (`getRewardsOverview`, `getRedemptions`, `getRedemption`, `approveRedemption`, `approveAllClear`, `rejectRedemption`, `retryRedemption`, `refundRedemption`, `getOffers`, `updateOffer`, `getPartners`, `getPartner`, `setPartnerStatus`, `addCodes`); it returns copies so cached query data never changes underneath. `hooks.ts` wraps them in TanStack Query (every write invalidates `["rewards"]`; lists poll every 2 s only while a top-up is delivering). `lib/rewards.ts` holds the review checks (`checkRedemption`, `riskOf`), labels and formatting. Request filters and the open request live in the URL (`status`, `partner`, `risk`, `open`). Statuses: pending (gold held) → processing (top-up with the partner) → fulfilled, or rejected/refunded (gold returned), or failed (retry/refund). The shared `src/components/ui/switch.tsx` primitive (Radix Switch, already a dependency) was added for the catalog.
- **Settings:** lazy authenticated `/settings` route with an Appearance section and one theme button. The page shows the current mode and switches immediately through the shared provider, without an API or separate state store. Add future preferences as sections in this feature; keep theme switching centralized here. RDI `/rdi/settings` remains the separate website-content settings screen.
- **Ads:** lazy `/ads-management` (overview: stage tiles, filters, every ad), `/ads-management/ad-requests` (the review queue, oldest first) and `/ads-management/reported-ads`, on super-admin's `/ads` routes. One detail sheet (`components/AdDetailSheet.tsx`) shows the creative, advertiser, targeting, gold (held, charged, returned), delivery, review and reports, and offers what the admin's permissions (`ads.read`, `ads.review`, `ads.manage`) and the ad's stage allow; reasons go through a dialog with AdBox's common reasons. Actions are awaited (`mutateAsync`) because the refetch can close the sheet. Gold moves on the server within a minute, never here.
- **Financials:** `/financials/gold-pricing` (every gold number, the store, Spotlight) and `/financials/advertisers-payment` (gold bought through Paystack, `payments.read`).
- **Dashboard:** `components/` renders widgets; `data/` holds current display datasets. Keep dashboard-specific charts here until another feature needs them. **Institutions across Ghana** (`DashboardInstitutionMap`, full width) is the dashboard's first live widget: `hooks.ts` → `api.ts` read super-admin `GET /institutions` (needs `institutions.read`; a 403 says so beside an empty map). The map in the middle is the 16 regions from `data/ghana-regions.ts` (geoBoundaries gbOpen GHA ADM1, © OpenStreetMap contributors, CC BY-SA 2.0; projected and simplified once, attribution shown under the map), shaded in five grey steps by institution count, with a dot per active institution at its town (`data/ghana-towns.ts`, `town|region` → longitude/latitude, looked up once on OpenStreetMap; unknown towns sit at the region's centre and say so) spiralled apart when they share a town. Dots use three validated categorical colours (`lib/institution-map.ts` groups the catalogue's 16 types: universities & tertiary, colleges of education, health & other colleges). The region list (left) is the keyboard path and selects a region; the selected region's institutions are listed on the right. Top Publishers sits under Earning Breakdown.
- **Videos:** `components/upload/` handles school selection and media composition; `components/folders/` handles folder creation and selection; `components/posts/` renders collections and details; `components/shared/` holds media preview and header components. Filters live in `hooks/`, browser metadata in `store/`, models in `types/`, and fixture content in `data/`.
- **RDI website:** `pages/` contains Home, About, Construction, Media, Solar, and Contact. `layouts/` supplies the shared website layout; `components/` groups division-specific UI and shared website controls. Static defaults live in `data/`, local images in `public/rdi-assets/`, and scoped styles in `styles/website.css`. Container queries respond to available width. Tabs, filters, project dialogs, and form feedback use component state. The contact form never transmits messages.
- **RDI CMS:** `cms/pages/` owns the page overview, editor, media library, and site settings. Reusable editor controls live in `cms/components/`. `cms/catalog.ts` and `cms/data/` describe editable sections, field defaults, collections, and assets. Website components read draft overrides through `useCmsText` and `useCmsCollection`; `CmsSection` controls visibility without adding layout wrappers. Shared contact settings use `useWebsiteContact`. The versioned draft and undo/redo history live in `cms/store.ts`, with validation/export in `cms/lib/document.ts` and image handling in `cms/lib/media.ts`. Uploaded image data is stored once and referenced from content by asset ID. Original assets are never deleted through the UI.

The CMS preview uses the same website components as the standalone website. Parent and iframe exchange validated drafts through `postMessage`, checking both origin and window identity. Storage events refresh saved drafts in other tabs; pending local changes are preserved. No preview or CMS interaction issues API requests. Backup export includes default content plus local changes, and import requires confirmation before replacing a draft. Schema version changes must include a deliberate migration or a clearly reported incompatibility.

## Adding a feature

1. Add its domain page and components under `src/features/<name>/`. Start with the smallest useful structure.
2. Add API services and Query hooks if it needs server data. Validate external data at service/form boundaries.
3. Add paths in `src/routes/paths.ts`, lazy routes in the feature's `routes.ts`, and export those routes from its `index.ts`.
4. Register the routes in `src/routes/router.ts` under the appropriate layout and guard.
5. Add navigation in `src/config/navigation.ts`; remove the corresponding pending definition when replacing a planned module.
6. Reuse shared controls and design tokens. Follow the responsive rules in `grid.md`.
7. Run `npm run check` and verify the affected user flow in the browser.

## Production integration boundaries

The organization and build checks are ready to support continued development. Full product readiness still depends on connecting dashboard data, upload publishing, Posts, header actions, and pending business modules to their services. RDI intentionally remains a local CMS and website UI: there is no remote storage, collaboration, publishing, or contact delivery. Historical CMS database reference files are retained in `database/rdi-cms/`, are disconnected from runtime code, and are never run by frontend setup or CI.
